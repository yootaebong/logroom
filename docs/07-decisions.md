# 07 · Decisions (ADR)

핵심 기술/제품 결정 기록. 형식: 컨텍스트 / 결정 / 근거 / 대안 / 결과.
번복하려면 새 ADR을 추가한다(기존 것 수정 금지).

---

### ADR-0001 · 로컬 온리, 클라우드 없음
- **컨텍스트**: AI 프롬프트·업무 기록은 극도로 민감. 사용자는 프라이버시가 최우선.
- **결정**: 모든 데이터는 로컬에만. 기본 상태 아웃바운드 네트워크 0.
- **근거**: 프라이버시=핵심 가치이자 세일즈 포인트. 백엔드 0 → 초고마진(솔로 상업화에 유리).
- **대안**: 클라우드 동기화 기본 — 기각(신뢰·비용·규제 부담).
- **결과**: 동기화는 미래 opt-in E2E 유료 기능으로만.

### ADR-0002 · Tauri v2 (not Electron)
- **컨텍스트**: 설치형 데스크톱 + 유료 배포 + 프라이버시.
- **결정**: Tauri v2(Rust core + React webview).
- **근거**: 작은 서명 설치파일, 내장 updater, secure-by-default. 프라이버시 제품 첫인상에 유리.
- **대안**: Electron(전부 TS, 빠른 출시) — 용량/메모리 불리로 기각. Rust 3곳만 얇게 써서 리스크 관리.
- **결과**: 로직 대부분 TS, Rust는 DB/인제스트/파일감시(+라이선스).

### ADR-0003 · 완전 비공개(proprietary), 오픈코어 아님
- **상태**: 대체됨(Superseded by ADR-0018)
- **컨텍스트**: 상업화 예정. 초기엔 오픈코어(코어 OSS) 검토했으나 사용자가 전면 비공개 선택.
- **결정**: 소스 전면 비공개, private 저장소, All Rights Reserved.
- **근거**: 사용자 의사. IP 보호.
- **결과(리스크)**: "진짜 로컬인가"를 오픈소스로 증명 불가 → **네트워크 투명성 페이지 + 공증 + (여력시)3자 감사**로 신뢰 대체.

### ADR-0004 · SQLite + FTS5(trigram) 로컬 스토어
- **결정**: rusqlite 번들 SQLite, 전문검색 FTS5 `trigram` 토크나이저.
- **근거**: 단일 파일·로컬·빠름. trigram은 한국어/CJK 부분검색에 강함(검색이 킬러 기능).
- **대안**: unicode61(가볍지만 CJK 약함) — 도그푸드 한글 검색 위해 기각.
- **결과**: 인덱스 다소 큼 감수. SQLite 3.51에서 trigram 지원 확인.

### ADR-0005 · 캡처 = 로컬 인제스트(127.0.0.1 + 토큰) + 파일 감시
- **결정**: 앱이 로컬 HTTP 인제스트를 열고, 파일감시(notify)로 세션 로그를 tail. push 소스(hook/확장)는 POST.
- **근거**: 툴마다 세션을 로컬 파일/DB에 남김(검증). 감시형은 외부 프로세스 불필요. 이중화로 유실 최소화.
- **결과**: `(source, external_id)` UNIQUE로 idempotent. 앱 꺼짐 구간은 cursor backfill.

### ADR-0006 · 통합 Event/Stream 모델, 스트림 = 소스 세션
- **결정**: 모든 소스를 Event/Stream으로 정규화. `stream_id = "<source>:<native session id>"`.
- **근거**: 검증 결과 3개 툴 모두 "세션 = 대화 / cwd = 프로젝트 / title 제공" 패턴 → 깔끔히 매핑.
- **결과**: 병렬 레인 = 겹치는 스트림. 상위 그룹(프로젝트/티켓)은 후속.

### ADR-0007 · 클로즈드 프리미엄 + Pro 구독 + 오프라인 서명 라이선스
- **상태**: 부분 대체됨 — "클로즈드" 부분은 ADR-0018 로 대체, Pro·라이선스 수익화는 별도로 다시 정한다
- **결정**: 무료(로컬 캡처)+Pro 구독(커넥터/AI요약/동기화). 라이선스는 Ed25519 서명키 로컬 검증. 결제는 MoR(Lemon Squeezy).
- **근거**: 로컬 앱 월정액 저항 → 커넥터의 지속 유지보수/동기화 서버비가 구독을 정당화. 오프라인 검증으로 프라이버시 유지.
- **결과**: M6에서 구현. 가격은 도그푸드 후 결정.

### ADR-0008 · macOS 우선, Windows 나중
- **결정**: 도그푸드/초기 판매는 macOS. Windows는 판매 확장 단계.
- **근거**: 개발자 본인 환경(macOS), 검증된 캡처 경로가 macOS 기준. 범위 축소로 속도.
- **결과**: 경로/키체인 등 macOS 가정. Windows는 M7에서 추상화 정리.

### ADR-0009 · 직접 배포 (Mac App Store 아님)
- **컨텍스트**: 캡처는 **타 앱의 세션 파일**(`~/.claude`, `~/.kiro`, `~/Library/Application Support/Kiro/…`) 읽기가 필수.
- **결정**: Mac App Store 배포 안 함. **직접 배포(.dmg) + hardened runtime + Apple 공증.**
- **근거**: App Store 샌드박스는 타 앱 데이터 경로 접근을 차단 → 캡처 불가. 비샌드박스 직접배포는 사용자 홈 내 파일 읽기 가능(대개 Full Disk Access 불필요).
- **대안**: App Store(발견성↑) — 캡처 불가로 기각.
- **결과**: 배포/업데이트는 자체 호스팅(서명 매니페스트). 결제도 MoR(ADR-0007)라 App Store 불필요. 첫 실행 시 필요하면 권한 안내.

### ADR-0010 · Claude Code 저장 진실소스 = JSONL, hook = 라이브 신호
- **컨텍스트**: hook(실시간)과 JSONL(완전) 두 경로가 같은 활동을 캡처 → 중복 위험(키 상이: `promptId` vs `uuid`).
- **결정**: **JSONL 파서만 영구 이벤트 저장**(`external_id=uuid`). hook은 스트림 활성/최근성 신호만 보내고 저장하지 않음.
- **근거**: 단일 저장 경로로 dedup 문제 원천 제거. hook은 저지연 UX, JSONL은 토큰/모델/툴까지 완전.
- **대안**: 양쪽 저장 + `promptId` 통일 upsert-merge — 복잡도↑로 기본 채택 안 함(필요 시 전환).
- **결과**: `03-capture`의 "중복 처리" 규칙과 일치.

### ADR-0011 · 마케팅 사이트와 앱 텔레메트리 완전 분리
- **컨텍스트**: 랜딩(`apps/web`)은 애널리틱스/이메일 수집 등 네트워크가 필요하지만, 앱은 "텔레메트리 0"이 핵심 가치.
- **결정**: 웹사이트의 추적/수집은 **사이트 내에서만**. 데스크톱 앱은 어떤 사용 데이터도 사이트/서버로 보내지 않는다.
- **근거**: 프라이버시 제품의 신뢰. 마케팅 편의가 앱 프라이버시를 침해하면 안 됨.
- **대안**: 앱에 opt-in 분석 심기 — 기본 off라도 분리 원칙 우선이라 사이트로 한정.
- **결과**: 랜딩은 `apps/web`으로 분리 배포(Vercel/CF Pages). 앱과 코드/도메인 경계 명확.

### ADR-0012 · 회고 중심 저장(essential body policy)
- **컨텍스트**: 도그푸드 DB 실측(2026-07) 결과 전체 1.1GB 중 FTS 인덱스 734MB(67%) + `tool_result.body` 201.8MB +
  `tool_use.metadata`(input 전문) 28.3MB로 tool 계열이 대부분을 차지하는 반면, 제품의 핵심 가치인
  prompt+response는 16MB(1.5%)뿐이었다.
- **결정**: 캡처 시 `tool_result.body`는 256자, `tool_use.metadata`의 input은 문자열화 후 512자로 절단해 저장한다
  (`inputPreview`로 대체). `prompt`/`response`는 정책과 무관하게 항상 전문 저장. FTS(`events_fts`)도 `prompt`/`response`
  타입만 인덱싱하도록 축소(트리거 WHEN 조건). 전역 설정 `capture.bodyPolicy`(`essential`(기본) | `full`)로 필요 시
  절단 없는 원문 저장으로 전환 가능. 기존 데이터는 `V2__essential_body.sql` 마이그레이션으로 소급 다이어트 + FTS 재구축.
- **근거**: 원문(코드 diff, 커맨드 출력 등)은 어차피 로컬 소스 파일/터미널 히스토리에 남아있어 "회고"(무엇을 언제
  물어봤고 어떻게 답했는지가 핵심) 용도로는 tool 계열 전문 보존의 한계효용이 낮다. 반면 prompt/response는 그 자체가
  유일한 기록이라 축소 대상에서 제외한다. FTS 인덱싱 범위 축소는 부수효과로 검색 노이즈(tool 출력 매칭)도 줄인다.
- **대안**: 전문 유지 + 별도 압축(zstd) blob 테이블로 분리 저장 — 조회 시 압축해제 경로·스키마 복잡도가 커서 기각.
  필요 시 `full` 정책으로 절단 없는 원문 저장을 선택할 수 있게 해 완전 손실을 막는 안전판을 남겼다.
- **결과**: 신규 캡처는 essential 정책 기본 적용(`config.rs::CaptureConfig::body_policy`, normalize.rs/kiro.rs 공유
  절단 규칙). 기존 DB는 `V2__essential_body.sql` 적용 직후 `VACUUM`으로 디스크 공간을 즉시 회수(ADR 없는 일반
  마이그레이션 정책에 "새 마이그레이션 적용 시 VACUUM" 규칙 추가, `db.rs::open_and_migrate`).
  - **보강(2026-07)**: Slack 커넥터(ADR-0015) 도입으로 `message`(사용자가 직접 쓴 메시지)가 새 이벤트
    타입으로 등장하면서, V2의 `type IN ('prompt', 'response')` FTS 조건이 tool 노이즈뿐 아니라 사용자
    콘텐츠인 `message`/`note`(수동 기록, 미래)까지 검색 불가로 묶어버리는 문제가 드러났다. `message`/`note`는
    tool 계열이 아니라 prompt/response와 동급의 사용자 콘텐츠로 재분류해 `V7__fts_user_content.sql`로 FTS
    인덱싱 범위를 `type IN ('prompt', 'response', 'message', 'note')`로 확장했다(tool_use/tool_result는
    계속 제외).

### ADR-0013 · 자동 업데이트: 아웃바운드 유일 예외 + 공증 없는 배포
- **컨텍스트**: ADR-0001/04-privacy-security의 "기본 아웃바운드 0" 원칙과, 실제 배포된 앱을 최신 상태로
  유지해야 하는 요구가 충돌한다. 또한 Apple 공증(ADR-0009)은 계정/비용/절차가 필요해 M5 시점에는
  준비되지 않았다.
- **결정**:
  1) **업데이트 체크는 "기본 아웃바운드 0" 원칙의 유일한 예외**로 명시한다. 단, 예외를 최소화하기 위해:
     체크 요청은 **버전 정보만**(현재 버전 문자열) 보내고 사용자 식별자·텔레메트리는 전혀 포함하지 않는다.
     `~/.logroom/config.json`의 `checkUpdates`(기본 `true`)로 **opt-out 가능**하다. 새 버전 발견 시
     자동 다운로드는 하지 않고 **다운로드·설치는 항상 사용자가 명시적으로 눌러야** 진행된다
     (`check_update`/`install_update` 커맨드, `docs/03-capture.md`가 아니라 이 문서 네트워크 정책 절에서
     추적).
     - **보강(2026-07)**: 최초 실행 시 릴리스 산출물이 구버전이어도 사용자가 바로 알 수 있도록 (a) 최초
       체크 대기를 60초→3초로 단축하고, (b) 구버전이면 배지보다 강한 **업데이트 모달**(UpdateModal)을
       띄운다. **설치는 여전히 모달의 "지금 업데이트" 클릭으로만** 진행하므로 "설치는 명시적" 원칙은
       불변이다(자동 설치·자동 재시작은 도입하지 않음 — 캡처/요약 작업 중 몰래 재시작하는 것이 프라이버시
       제품의 사용자 통제 원칙에 어긋나기 때문). "나중에"는 세션 한정 dismiss라 다음 실행 때 다시 뜬다.
  2) **공증 없이 배포**한다(ad-hoc 서명 + 직접 배포 유지, ADR-0009). 대신 업데이트 파일 자체의 무결성은
     Tauri updater의 **minisign 서명**(`tauri.conf.json`의 `plugins.updater.pubkey`, 개인키는 저장소 밖
     `~/.tauri/*.key`)으로 검증한다. Gatekeeper가 "확인되지 않은 개발자" 경고를 띄우면 사용자가 우클릭
     "열기"로 수동 허용해야 함을 다운로드 페이지/첫 실행 안내에 고지한다.
- **근거**: 자동 업데이트 없이는 버그·보안 수정을 사용자에게 전달할 방법이 없어 프라이버시 제품으로서도
  손해(구버전에 남은 취약점)다. 체크 요청의 정보량을 "버전 문자열뿐"으로 최소화하고 opt-out을 제공하면
  "기본 아웃바운드 0" 정신(최소 수집·명시적 네트워크·opt-out)은 유지된다. 공증은 Apple Developer
  Program 가입+공증 파이프라인 구축이 필요해 도그푸드 단계 속도를 늦춘다 — minisign 서명이면 업데이트
  무결성은 이미 보장되므로 공증을 M5의 필수 관문으로 두지 않는다.
- **대안**:
  - 업데이트 체크도 기본 off(수동 확인만) — 기각. 실사용자 다수가 절대 수동으로 확인하지 않아 보안 수정
    전달력이 떨어진다. 대신 "버전만 요청 + opt-out" 조건으로 기본 on을 정당화했다.
  - M5에서 바로 Apple 공증 도입 — 기각(계정/비용/시간). M6로 이연, 공증 전까지는 Gatekeeper 수동 허용
    고지로 신뢰 갭을 메운다.
- **결과**: `check_update`/`install_update`는 Rust 커맨드로만 노출(FE가 업데이트 서버에 직접 fetch하지
  않음 — 네트워크 발생 지점을 코드에서 한 곳으로 고정해 감사 가능하게 유지). 백그라운드 체크는 앱 시작
  60초 후 + 24시간 간격(`update.rs::spawn_periodic_check`). `docs/04-privacy-security.md` 네트워크 정책
  표를 이 결정에 맞춰 갱신. M6에서 Apple 공증 도입 시 이 ADR에 후속 ADR로 갱신(기존 항목은 수정하지 않음).

### ADR-0014 · 포지셔닝 = 범용 작업 기록기(AI-first)
- **컨텍스트**: 도그푸드를 진행하며 확신이 선 지점이 있다 — 매일 실제로 가치를 느끼는 순간은 "AI를 썼다"가
  아니라 "그때 내가 뭘 했는지가 기억난다"는 것이었다. 초기 포지셔닝("AI 시대에 여러 작업을 동시에 굴리는
  나를 위한 로컬 온리 활동 기록기")은 캡처 소스를 AI 툴로 한정 짓는 인상을 줘, 오늘 지원 소스(Claude Code,
  Kiro 2개)와 장기 방향(Slack·Linear·Figma 등 SaaS 커넥터, `docs/00-product.md` 스코프의 "나중" 항목) 사이의
  간극을 가린다.
- **결정**: 제품 포지셔닝을 "AI 작업 기록기"에서 **"범용 작업 기록기"** 로 전환한다. AI는 계속 첫 번째이자
  가장 강력한 캡처 소스로 유지하되(오늘 실제로 동작하는 유일한 소스), 랜딩/문서의 프레임은 "일이 벌어지는
  모든 곳(AI 세션·SaaS·수동 기록)"으로 넓힌다. 단, 과장 금지 — Today(오늘 지원: Claude Code·Kiro)와
  Roadmap(예정: Gemini·Slack·Linear·Figma·Jira 등)을 카피에서 항상 명확히 구분한다.
- **근거**: (1) 시장 확장 — "AI 툴 병렬 사용자"보다 "일이 여러 툴에 흩어진 지식노동자" 시장이 훨씬 크다.
  (2) 이미 있는 커넥터 로드맵(`docs/00-product.md` "나중" 스코프: Linear·Slack·Jira·Figma)과 포지셔닝을
  맞추는 것뿐 — 새 기능 약속이 아니다. (3) 로컬 온리·프라이버시라는 핵심 차별점(ADR-0001)은 캡처 소스가
  많아질수록 더 강해진다 — "모든 걸 로컬에만 모은다"는 약속은 소스 1개보다 여러 개일 때 값어치가 크다.
- **대안**: 포지셔닝 유지("AI 전용 기록기"로 좁게 유지) — 기각. 오늘의 실제 지원 소스(2개)에 비해 카피가
  이미 과장돼 있었고, 장기 로드맵과도 어긋나 개발이 진행될수록 포지셔닝을 다시 바꿔야 하는 문제가 있었다.
- **결과**: `docs/00-product.md`의 한 줄 정의·문제 정의·차별점 1을 이 결정에 맞춰 갱신. `apps/web`
  랜딩(en/ko)의 hero·problem·features·sourceStrip 카피를 전면 반영. 캡처 우선순위·구현 순서(Claude Code →
  Kiro → Gemini → SaaS 커넥터)는 기존 로드맵을 그대로 유지 — 이번 결정은 포지셔닝/카피에 한정되고 기능
  범위나 일정을 변경하지 않는다.

### ADR-0015 · 커넥터 아키텍처 — 로컬 폴링 + v1 수동 토큰
- **컨텍스트**: 첫 SaaS 커넥터(Slack)를 붙이며 두 축을 결정해야 했다 — (1) 서버 없이 로컬 온리 원칙
  (ADR-0001)을 지키면서 SaaS 데이터를 어떻게 가져올지, (2) 토큰 발급 방식을 OAuth로 바로 갈지 수동
  입력으로 시작할지. Slack은 실시간 푸시가 필요하면 Events API(공개 HTTPS 엔드포인트 또는
  Socket Mode 상시 연결)를 쓰지만, 전자는 반드시 인터넷에 노출된 서버가 필요해 "서버 경유 0" 원칙과
  정면 충돌하고 후자(Socket Mode)도 팀 앱 등록+토큰 로테이션 등 v1 범위를 넘는 운영 부담이 있다.
- **결정**:
  1) **사용자 기기에서 직접 폴링**한다. 앱(Rust 백그라운드 태스크)이 주기적으로(기본 5분,
     설정 가능) Slack Web API `search.messages`를 직접 호출해 새 메시지를 가져온다. 서버 경유는
     0 — 캡처 파이프라인은 기존 파일감시(watch.rs)와 동일하게 "인제스트 직전 스크럽 →
     캡처 일시정지 체크 → `db::ingest()`" 규칙을 그대로 공유한다.
  2) **v1 토큰은 수동 발급 user token(`xoxp-`)** 이다. 사용자가 `api.slack.com/apps`에서 직접 앱을
     만들고 `search:read` User Token Scope를 추가해 설치한 뒤 토큰을 앱 설정에 붙여넣는다. OAuth
     설치 플로우(원클릭 연결)는 **보류**한다.
  3) **429(rate limit)는 `Retry-After` 헤더를 그대로 준수**하고, 이후 연속 실패에는 지수 백오프
     (최대 5분 상한)를 적용한다. 그 외 에러는 로그만 남기고 다음 폴링 주기에 재시도한다.
- **근거**:
  - Events API 기각 — 로컬 온리 제품은 인바운드 HTTPS 엔드포인트를 상시 열어둘 서버가 없다(있다면
    ADR-0001의 "로컬에만 저장"이 아니라 "서버를 거쳐 로컬로 전달"이 되어 신뢰 모델이 달라진다).
    Socket Mode도 검토했으나 앱 매니페스트/토큰 관리 복잡도가 v1 대비 과하고, 폴링만으로도 "회고
    중심 기록"(ADR-0012, 실시간성보다 완전성이 우선)이라는 제품 목적에는 충분하다.
  - OAuth 보류 — OAuth 설치 플로우는 자체 redirect 엔드포인트(최소 로컬 루프백 리스너) 또는 Slack
    앱 검수(app distribution)가 필요해 v1치고 과한 선투자다. 수동 토큰은 사용자가 스코프를 직접
    확인하며 발급하므로 최소 권한 요청("search:read" 하나)을 스스로 검증할 수 있다는 부수 이점도
    있다(프라이버시 투명성, ADR-0003의 신뢰 보완 수단과 결이 같다).
  - 429 준수 — Slack Web API의 명시된 계약(`Retry-After` 헤더)을 어기면 워크스페이스 전체의 다른
    통합에도 영향을 줄 수 있어, 단일 사용자 로컬 폴러라도 이 신호를 존중하는 것이 최소한의 예의이자
    장기 안정성의 조건이다.
- **대안**:
  - Events API(서버 필요) — 기각(위 근거).
  - OAuth v2 설치 플로우 — 기각(v1 범위 초과), **후속 검토 대상**으로 남긴다. 사용자 수가 늘고
    "복사-붙여넣기 토큰"의 UX 마찰이 실제 이탈 원인으로 확인되면 로컬 루프백 리스너 기반 OAuth로
    전환한다.
  - 고정 짧은 폴링 주기(예: 30초) — 기각. `search.messages`는 Tier 2 레이트리밋(분당 호출 수 제한)
    이라 과도한 폴링은 429만 유발한다. 기본 5분이 "회고 기록" 목적에는 충분하고 설정으로 조정
    가능하게 했다.
- **결과**: `apps/desktop/src-tauri/src/capture/slack.rs`(폴러+정규화)와 `docs/08-connectors.md`(커넥터
  원칙 + Slack v1 스펙)로 구현. 헬스 판정은 파일감시(mtime 기반)와 달리 "폴 성공 시각"
  (`capture_cursors.updated_at` 재사용)만으로 계산한다 — 파일 root 개념이 없는 폴러형 소스의 첫
  사례라 `capture/health.rs`에 파일감시와 다른 판정 경로를 추가했다. Pro 게이팅(무료/유료 경계)은
  M6에서 구현하고, 이번 v1은 게이팅 없이 기능만 제공한다(설정 UI에 "Pro 예정" 표시만 선행).

### ADR-0016 · 수익화 전 "지불 이유" 선행(M7 → M6 순서 역전) + 일일 AI 요약 엔진 이중화
- **컨텍스트**: 커넥터 3종(Slack·GitHub·Linear) 완성 후 냉정 평가 결과 — 기록·정렬 자체는
  "비타민"(주 1~2회 15분짜리 고통)이라 지불 전환이 어렵고, 같은 카테고리 선례(Rewind.ai)도 수익화에
  실패했다. 사용자(개발자 본인) 도그푸드에서도 "현 상태로는 돈 안 내고 쓸 것 같다"가 확인됐다.
  ADR-0007의 커넥터=Pro 게이트는 사용자 입장에서 **투입**(더 많이 기록) 쪽에 있는데, 지불 심리는
  **산출물**(요약·리포트·재개 컨텍스트)에서 발생한다. 한편 요약에 쓸 LLM은 로컬 온리
  원칙(ADR-0001)과의 양립 방법이 필요하다.
- **결정**:
  1) **M6(라이선스·결제)를 M7 뒤로 순연**한다. 순서: M7-① 일일 AI 요약 → M7-② 재개 브리핑
     ("어디까지 했지" 패킷 → 클립보드 → 에이전트 재투입) → 본인 2주 도그푸드로 "돈 낼 만하다"
     검증 → 그 후 M6. 지불 게이트 경계(커넥터 vs 요약/리포트)도 M6 시점에 재논의한다
     (ADR-0007 부분 재검토 예고).
  2) **요약 엔진은 이중화**한다 — 얇은 추상화(SummaryEngine) 아래 두 백엔드:
     (a) **Claude Code CLI 재활용**(`claude -p` headless): 타겟 유저 대부분이 이미 구독자라
     한계비용 0·설정 0클릭. (b) **BYO Anthropic API 키**: CLI 없는 유저용, 커넥터 토큰과 동일한
     마스킹 왕복·0600 관례. 설정은 "자동(CLI 감지 시 우선)/CLI/API 키" 3택.
  3) **요약 프롬프트는 en/ko 이중화**한다(사용자 명시 요구). 앱 로케일(resolved locale)에 따라
     지시문을 선택하고 **요약 출력 언어 = 앱 언어**로 고정한다 — i18n 테이블(ui.ts)과 같은
     "타입 안전 키 + en/ko 병기" 패턴을 프롬프트에도 적용한다.
  4) **프라이버시 계약**: 요약은 명시적 opt-in + **전송 발췌 미리보기** 제공 + 캡처 일시정지 시
     요약 아웃바운드도 중단(커넥터와 동일 규칙). CLI 백엔드의 **자기 캡처 루프**(요약 호출 자체가
     `~/.claude*` 감시 대상에 JSONL로 남음 — 실측 확인) 차단은 **cwd 고정(`~/.logroom/summarizer`) +
     해당 프로젝트를 정규화 단계에서 제외(policy 하드코딩)** 로 한다. 최초 안이었던
     `CLAUDE_CONFIG_DIR` 격리는 **기각** — CLI 인증 정보가 config dir에 있어 격리하면 로그인이 풀린다
     (프롬프트 실검증 중 발견).
- **근거**:
  - 로컬 모델 v1 기각 — 실사용 데이터가 한국어+기술 용어 중심이라 3B급은 품질 미달, 쓸만한 최소선
    (7~8B, 4bit)은 +5GB로 "8MB 가벼운 로컬 앱" 정체성과 충돌하며 러타임 통합 공수도 커넥터 1개분
    이상. 요약 품질이 곧 상품이라 최상급 모델로 시작하는 것이 맞다.
  - BYO/CLI는 서버 경유 0 유지 — 전송처가 사용자 본인 계정(Anthropic)이라 우리 서버·비용·책임이
    없다(커넥터의 "수동 토큰" 결과 동일한 신뢰 모델).
- **대안**: 자사 프록시 서버(기각 — ADR-0001 위반+서버비) / 로컬 모델 기본(기각 — 위 근거,
  **Ollama 설치 감지 연동을 후속 옵션**으로만 남김) / M6 선행(기각 — 지불 이유 없이 계산대부터
  세우는 순서).
- **결과**: v0.5.0(Linear+다이제스트 개편)까지 배포 완료 후 M7-① 착수. 구현 산출물(예정):
  요약 모듈(Rust)+Settings "요약" 섹션+다이제스트 상단 요약 카드, 결과는 DB 캐시(날짜별 1회,
  재생성 버튼). 후속 아이디어로 티켓 크로스링크(TICKET-N 커버리지 18% 실측 — 컨벤션 정착 또는
  AI 매칭 필요)를 로드맵에 기록.

### ADR-0017 · 업무평가서(분기 평가·월간 점검) — 요약 위에 판단 한 칸
- **컨텍스트**: 요약(일간→주간→월간)은 "무엇을 했나"를 사실 로그로 답한다(v5~v9 — 불릿에 평가어
  금지). 사용자는 그다음 질문 "잘했나, 무엇이 부족했나"를 원했다 — 회사 자기평가서를 쓸 때 기록을
  뒤지는 수고가 크다. 요구: 섹션 3개(잘한 것 / 못한 것 / 채우면 좋은 것), 기준은 대기업·중소기업을
  아우를 것.
- **조사**(2026-09-23, 원문·출처 전체는 작업 공간 `RESEARCH/LOGROOM_PERFORMANCE_REVIEW_CRITERIA_2026-09-23.md`):
  - 규모와 무관하게 반복되는 축은 **성과·임팩트 / 실행·완결 / 전문성·문제 해결 / 협업·소통 /
    성장·학습** 다섯 개다(국내: 삼성·SK하이닉스·LG전자·현대차·카카오·당근, 중소기업 인사평가표·
    레몬베이스·flex / 해외: Google·Meta·Microsoft·Amazon·Adobe·Deloitte·SHRM·HBR).
  - 공통 요구는 **증거 기반 서술**(Meta diff 링크, Amazon 구체 성과 3~5건, 국내 STAR 기법).
  - 세 칸은 회고 표준 KPT(Keep/Problem/Try)와 그대로 대응한다. "못한 것"은 상황→행동→영향(SBI)
    문형이 권고되고, 성격 단정은 국내외 가이드가 공통으로 금지한다.
  - 활동량은 성과가 아니다 — SPACE 프레임워크(2021), McKinsey 개발자 생산성 측정안(2023)에 대한
    비판, Goodhart 법칙.
  - 실측: Linear 이슈의 약 30%가 시작한 달 안에 끝나지 않는다(7월 124건 중 34건, 8월 44건 중 17건
    미완료·이월). 한 달 단위로 "못한 것"을 판단하면 경계 효과가 잡음이 된다.
- **결정**:
  1) **분기 평가가 본체, 월간은 점검**이다. 월간 점검은 같은 틀에 두 번째 칸을 "밀린 것·막힌 것"으로
     바꾸고 이월을 실패로 쓰지 않는다. 기간은 달력 분기("YYYY-Qn").
  2) **요약 위에 한 칸**: 분기는 월간 요약 3개, 월간 점검은 주간 요약들을 입력으로 쓴다(원본 재발췌
     없음). 빠진 하위 요약은 한 단계만 생성하고(그 아래는 `CachedOnly`), **기간이 끝나기 전에 만든
     하위 캐시는 다시 만든다**(9/10에 만든 9월 요약으로 3분기를 평가하면 9월 후반이 빠진다). 평가서
     한 번의 LLM 호출은 최대 하위 3회 + 평가 1회.
  3) **숫자는 DB, 판단은 LLM**: 사실 신호(Linear 완료·취소·기간 말 미완료·30일 정체, 시작→완료
     중앙값, GitHub PR·이슈·리뷰)는 SQL로 세어 발췌에 박는다. 프롬프트는 인용만 시킨다.
  4) **판단을 근거에 묶는 규칙**(프롬프트에 고정, 테스트로 보호): 점수·등급 금지, 활동량만으로 판단
     금지, 성격 단정 금지, 발췌에 없는 성과 금지, 기간 경계를 넘긴 일 자체는 "못한 것"이 아님,
     기록에서 안 보이는 것은 "하지 않았다"가 아니라 "기록에서 보이지 않는다". 총평 줄에 **근거 범위**
     (기간·프로젝트·통계, 회의 등 기록 밖 일은 반영 안 됨)를 적는다.
  5) **입력**: 포함 프로젝트 선택(회사 평가에 낼 때 개인 프로젝트 제외 — 하위 요약의 `## {프로젝트}`
     섹션과 사실 신호를 같은 표시명으로 좁힌다), 기간 목표(선택 — 있으면 목표 대비), **평가 프로필**
     (직무·연차 구간·팀원 관리 여부, 선택). 연차가 있으면 기대 수준을 맞춘다(엔지니어 레벨 기준 —
     주니어: 맡은 일 완수 / 미들: 스스로 설계·책임 / 시니어: 여러 과제·팀에 걸친 영향 / 리드: 팀
     성과·사람의 성장).
  6) **연봉은 받지 않는다.** 평가 기준을 바꾸지 못하면서(기업은 평가로 보상을 정하지, 보상으로
     평가하지 않는다) 매 생성마다 프롬프트에 실려 외부로 나간다. 프로필은 요약 설정과 별도 최상위
     키(`reviewProfile`)에 두고, 발췌에 그대로 들어가므로 미리보기로 전송 내용을 확인할 수 있다.
- **대안**: 월간 평가를 본체로(기각 — 위 실측, 경계 효과) / 점수·등급 산출(기각 — 활동 로그로는
  성과를 잴 수 없고, 등급은 오히려 신뢰를 깎는다) / 원본 이벤트 재발췌(기각 — 분기 30만 건, 요약
  계층을 두는 이유와 반대) / 온보딩에서 프로필 받기(기각 — 평가서를 안 쓰는 사용자에게 마찰; 설정 +
  평가서 첫 사용 시 인라인으로 받는다).
  7) **보고서 모양은 화면이 그린다.** AI는 구조가 정해진 텍스트만 쓴다(`- **요지** — 설명 [축]
     (근거)`). 카드·축 칩·근거 칩은 FE가 파싱해 그린다. HTML·표·차트를 AI에게 만들게 하면 출력이
     몇 배로 늘고 깨지기 쉽다. 그리는 데 드는 토큰은 0이다.
  8) **작업량 차트는 "기록된 활동"이라는 맥락이다.** 숫자 타일, 주별(월간은 일별) 활동 추이, 프로젝트
     비중을 넣는다. 전부 생성 시점의 DB 스냅샷(`performance_reviews.stats`)이라 다시 열어도 AI가 본
     숫자와 어긋나지 않는다. 단위가 다른 세 계열(요청·도구 활동·Linear 완료)은 한 축에 겹치지 않고
     작은 차트 셋으로 나눈다. AI 발췌에는 넣지 않는다 — 요청 수는 AI 에이전트 사용량에 좌우돼서 노력의
     척도가 못 된다.
  9) **시간·요일 분포는 옵션(기본 꺼짐)**이다(결정 2026-09-23). 요일×시 히트맵과 "평일 9~18시 밖
     비중·주말 비중"을 보여 준다. 감시 도구처럼 읽힐 수 있어 사용자가 켤 때만 그린다.
- **결과**: `summary/review.rs`(발췌·신호·스냅샷·캐시) · `prompts.rs` `PROMPT_REVIEW_*`(버전
  `REVIEW_PROMPT_VERSION`) · V12 `performance_reviews` · 커맨드 6개 · 요약 뷰 "평가" 스코프
  (`ReviewReport.tsx` 보고서 렌더) · 설정 "평가 프로필".

### ADR-0018 · 2026-10 MIT 오픈소스 전환(ADR-0003 대체)
- **컨텍스트**: ADR-0003(전면 비공개)의 결과로 "진짜 로컬인가"를 코드로 증명할 수 없어, 투명성 페이지·공증·3자 감사로 대신하려 했다. 공증은 하지 않기로 했고(ADR-0013) 3자 감사는 여력이 없다 — 로컬 전용이라는 핵심 주장을 사용자가 확인할 길이 없었다.
- **결정**: 소스를 MIT 라이선스로 공개한다. 공개 저장소는 현재 트리를 **커밋 1개로 새로 시작**하고, 이전 커밋 기록은 비공개 저장소에 보관한다.
- **근거**: 신뢰(로컬 전용·텔레메트리 없음)를 누구나 코드로 검증할 수 있게 한다. 이전 기록에는 개인·업무 흔적이 섞여 있어 그대로 공개하지 않는다.
- **대안**: 비공개 유지 + 투명성 페이지 — 기각(검증 불가 문제가 그대로). 오픈코어(일부만 공개) — 기각(캡처·저장 경로가 공개 범위 밖이면 검증 효과가 없다). 기록 전체 공개 — 기각(이력 정리 비용·노출 위험).
- **결과**: `LICENSE`(MIT)·루트 `README.md`·`CONTRIBUTING.md` 추가, 문서의 비공개 전제(04-privacy-security 신뢰 근거 등) 갱신. 공개 전 트리에서 회사·개인 흔적(레포 이름·티켓 키·로컬 경로)을 예시 이름으로 바꿨다. 수익화 계획(ADR-0016 등)은 별도 결정으로 다시 정한다.
